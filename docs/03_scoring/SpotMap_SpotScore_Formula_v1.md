# SpotMap — SpotScore Formula v1.0

**Статус:** расчетная спецификация + правила доверия, рейтинга и ранжирования · **Дата:** 11.11.2026.  
**Исполняемый прототип:** `spotmap_score_v1.py` + `test_spotmap_score_v1.py`.

## 1. Назначение и принцип

**SpotScore** оценивает качество спортивного объекта по нормализованным измерениям **0–100**. Он не равен:

- `MatchScore` (насколько место подходит конкретному человеку);
- `Rideability Score` (пригодность условий для катания в определённый момент);
- `Data Confidence` (насколько доказанным данным можно доверять);
- `Freshness` (давность последнего подтверждения);
- рейтингу популярности Telegram или числу подписчиков;
- цене, рекламному бюджету и спонсорскому размещению.

**Объект расчета (subject):** `club`, `spot` или `cable_installation`, но **раздельно**; нельзя механически переносить оценку одного клуба на весь водоём либо оценку парка на каждую установку. В MVP главная коммерческая карточка получает `club SpotScore` в контексте выбранного спота (при нескольких площадках используем ключ `(club_id, spot_id)`), а cable-installation — отдельный `installation SpotScore`, когда есть данные.

## 3. Откуда берутся оценки доменов

Для каждого домена `d` храним наблюдения `x_(d,i)` от 0 до 100, включающие:

1. **Структурированную экспертную оценку по опубликованной рубрике**, где каждый подпункт имеет критерии и доказательства; один экспертный аудит не означает госаккредитацию.
2. **Структурированные оценки пользователя после посещения** по шкале 1–5.
3. **Проверенные операционные факты**, которые могут участвовать в экспертной рубрике (наличие/состояние, процедуры, характеристики), но **не заменяют субъективную оценку автоматически**.

Преобразование отзыва в 100-балльную шкалу:

\[
x=25(r-1), \quad r \in \{1,2,3,4,5\}
\]

1 звезда = 0, 3 = 50, 5 = 100. Оценка `0` допустима только как осмысленная низкая оценка, **не как отсутствие отзыва**.

### Экспертная рубрика (пример)

`equipment / wakesurf`:

| Подкритерий | Вес внутри домена | Метод |
|---|---:|---|
| подтверждённая пригодность катера/волны под заявленные уровни | 35% | перечень моделей и спортивный аудит |
| состояние оборудования и досок | 30% | независимое наблюдение / документы |
| выбор досок/размеров | 20% | верифицированный каталог |
| актуальность обслуживания / прозрачность | 15% | проверяемые сведения, без догадок |

Если недостаёт критических подпунктов, эксперт обязан выставить **`assessment_incomplete`**, а не автоматически 0/100 или 100/100.

`course_setup / cable`:

| Подкритерий | Вес | Метод |
|---|---:|---|
| пригодность конфигурации под заявленные уровни | 30% | схема/характеристики трассы |
| состав и распределение фигур, их подтвержденный статус | 30% | проверенные installation_features |
| управляемость скорости / учебный режим | 20% | паспорт установки |
| удобство стартовой/выходной зон | 20% | проверка на месте/источник |

Рубрики версионируются и не меняются задним числом без пересчёта всех сравниваемых объектов.

## 4. Вес наблюдения

### Базовые веса

- независимый экспертный аудит: `base = 3.0`;
- отзыв после **подтверждённого посещения**: `base = 1.0`;
- непроверенный отзыв: `base = 0.35`;
- отзыв владельца / сотрудника о собственной площадке: **`base = 0`**, не учитывается;
- синтетические, заблокированные и flagged-fraud отзывы: `base = 0` до разбора.

### Коэффициент времени

\[
T_i = e^{-\mathrm{age\_days}_i/365}
\]

Через 365 суток вклад уменьшается примерно до `0.368`, но историческая запись остаётся в audit.

### Полный вес

\[
w_i = \mathrm{base}_i \times T_i \times \mathrm{fraudFactor}_i
\]

где `fraudFactor ∈ [0,1]` (только из внутреннего антифрод-процесса). Для одного автора/домена/объекта учитывается **не более одного отзыва за 90 дней** (для MVP — последний валидный); отсутствие идентификатора автора не даёт обходить лимит: агрегировать и лимитировать по защищенному abuse-идентификатору.

Дополнительно ограничивать дублирующиеся экспертные оценки одного аудитора на протяжении одного контрольного периода. Аудиторам нельзя начислять дополнительные веса за статус владельца объекта.

## 5. Шринкаж — устойчивость к одному отзыву

Для каждого домена с хотя бы одним допустимым наблюдением вычислить:

\[
n_d = \sum_i w_i
\]

\[
D_d = \frac{\kappa \mu + \sum_i w_i x_i}{\kappa+n_d}
\]

Параметры MVP: `μ = 65` (нейтральный **технический prior**, не эмпирический средний рынка), `κ = 3` (сила prior; требуют калибровки на пилоте). `D_d = NULL`, если `n_d=0`.

**Следствие:** одна пятёрка (100) с подтверждённого визита и свежестью 1.0 не даёт домену 100: `D=(3×65 + 1×100)/4=73,75`. Это защищает от рейтингового «всплеска» при 1–2 отзывах.

## 6. Coverage и правила публикации

\[
C = \frac{\sum_d W_d \cdot \mathbb{1}(n_d \ge 1.0)}{\sum_d W_d}
\]

`C` находится от 0 до 1. Домены с `0 < n_d < 1` участвуют в осторожной усредненной оценке, но **не считаются достаточно покрытыми** для coverage. Для математики итогового качества берём только домены с `n_d>0`; отсутствие домена не подставляет 0.

Коэффициенты и пороги подлежат А/А-проверке на пилотных данных. До неё — **предложенный базовый канон**, не «проверенная рыночная формула».

### Условия статусa

**`UNRATED` — без публичной оценки:**
- `C < 0.65`; или
- суммарный `n_total < 4.0`; или
- нет независимой проверки **фактов безопасности** (`safety_check_verified = false`); или
- конфликтующие критические данные/неясная идентичность;
- невозможна оценка конкретного субъекта/дисциплины.

**`PRELIMINARY` — оценка с явной пометкой:**
- `C ≥ 0.65`, `n_total ≥ 4.0`;
- проверен минимальный safety-checklist;
- отсутствуют активные критические инциденты;
- пока нет основания считать рейтинг полностью проверенным.

**`VERIFIED` — данные достаточны для устойчивой оценки:**
- `C ≥ 0.85`, `n_total ≥ 12.0`;
- проверен safety-checklist;
- есть ≥2 независимых source groups и ≥3 подтвержденных посещения **либо** независимый углублённый аудит;
- не обнаружены незакрытые критические нарушения/конфликты.

**`RESTRICTED` — ограничено:**
- подтверждённый активный критический риск безопасности → **публичный SpotScore не показывать как рекомендацию**, карточку снабжать предупреждением и направлять на перепроверку; это не обвинение и не публичная сертификация, решение документируется модератором.

**Важно:** в `UNRATED` реальная карточка остаётся видимой на карте при геоподтверждении и публикуемой информации; отсутствие рейтинга не означает отсутствие клуба.

## 7. Итоговый SpotScore

Для доменов с наблюдениями:

\[
S_{raw} = \frac{\sum_{d:n_d>0} W_d D_d}{\sum_{d:n_d>0} W_d}
\]

Если выполнены гейты, `SpotScore = round_half_up(S_raw)` до целого 0–100. В JSON отдавать дополнительно `raw_score` (precision 2), `profile_version`, `coverage`, `status`, массив contributions и дату перерасчета. Если гейты не выполнены — `score = null`, а **не 0**.

**Почему не вставляем Data Confidence в 5% рейтинга:** доверие к доказательству и качество — разные явления. Иначе новая достойная площадка системно проигрывает за «молодую» карточку даже при хорошем спортивном качестве. Confidence и Freshness должны влиять на **объяснение и силу рекомендации**, но не подменять оценку качества.

## 8. Recommendation rank (отдельно от оценки качества)

После отбора по дисциплине, географии, статусу работы и ограничениям:

\[
RankScore = 0.50\cdot Match + 0.25\cdot SpotScore + 0.15\cdot TravelConvenience + 0.10\cdot Trust
\]

Все величины 0–100; для `UNRATED` вместо качества используется `NULL` и система **нормализует веса доступных факторов** с пометкой «качество не оценено», **не подставляя ложную среднюю оценку**. Отдельно: при `critical safety` или ошибочном типе дисциплины объект не участвует в рекомендации независимо от ранга. Платные позиции всегда отдельным блоком с пометкой `Реклама`, не меняют `RankScore` и `SpotScore`.

Профиль пользователя, погода и доступность позже подключаются к Match и Rideability с explainability. `MatchScore` — персонализирован и нестабилен во времени; его **не хранить как общую оценку клуба**.

## 9. Data Confidence (отдельный показатель)

Для поля:

- источник подтверждён и релевантен текущему объекту;
- есть точная дата проверки факта;
- минимум два независимых источника для спорных утверждений;
- отсутствуют неразрешённые противоречия;
- законность и доступность доказательств соблюдена.

Предлагаемый confidence-индекс `K∈[0,100]`:

| Фактор | Вес |
|---|---:|
| надежность первоисточников | 35 |
| независимое подтверждение | 25 |
| свежесть ключевых фактов | 20 |
| разрешённость конфликтов | 20 |

**Нужна ручная и автоматическая верификация компонент.** `K<50` Low, `[50,80)` Medium, `>=80` High. Глобальный `K` — агрегат **важных текущих полей**, а не процент «заполненных строк». Не присваивать High лишь на основании Telegram-популярности или того, что бот успешно скачал страницу.

## 10. Freshness по классу факта

Рекомендованные **SLA проверки** (не автоматическая дата устаревания истины):

| Класс факта | Цель перепроверки |
|---|---:|
| цены/свободные слоты | ≤14 дней в сезон (слоты — только real-time provider) |
| режим работы/сезонный статус | ≤7 дней в сезон |
| катер и доступность установки | ≤30 дней |
| состояние фигур и критические инциденты | событие сразу; регулярная проверка ≤14 дней |
| контакт | ≤90 дней |
| геометрия/адрес | ≤180 дней либо при изменении |
| профиль тренера | ≤60 дней |
| исторический факт | бессрочно с сохранением исходной даты |

**Freshness status** `fresh / due / stale / disputed` рассчитывается по критичности поля и сроку, а не одной фиктивной дате для всего объекта.

## 11. Price / Value (отдельная рубрика)

`value` — не «чем ниже цена, тем выше рейтинг». В расчёте домена оценивается пакет: качество тренировки, длительность, включённая экипировка, квалификация и сравнимые предложения того же сегмента/региона. Нельзя давать 100 только за низкую цену или 0 только за премиальную цену. Если нет подтверждённой цены или пакета — домен `value` остаётся отсутствующим, coverage снижается; не подставлять 50.

## 12. Пример расчёта (синтетический для проверки арифметики)

Профиль `wakesurf_v1`. Предположим, есть **одна свежая независимая экспертная оценка** на каждый домен, каждая с весом `3`, а чек-лист безопасности подтверждён; все оценки в порядке таблицы:

| Домен | W | Эксперт x | n | Posterior D=(195+3x)/6 |
|---|---:|---:|---:|---:|
| riding_conditions | 0.20 | 90 | 3 | 77.50 |
| coaching | 0.15 | 85 | 3 | 75.00 |
| equipment | 0.15 | 88 | 3 | 76.50 |
| safety | 0.20 | 92 | 3 | 78.50 |
| service | 0.10 | 80 | 3 | 72.50 |
| infrastructure | 0.10 | 70 | 3 | 67.50 |
| value | 0.10 | 75 | 3 | 70.00 |

`C=1`, `n_total=21`; `S_raw = 0.20×77.5 + 0.15×75 + 0.15×76.5 + 0.20×78.5 + 0.10×72.5 + 0.10×67.5 + 0.10×70 = 74.925 → 75`.

**Статус:** PRELIMINARY, потому что проверены домены, но нет второго независимого источника и трёх подтверждённых визитов. Это иллюстрирует важнейший принцип: **высокая полнота не равна полной независимой верификации**. Если safety-check отсутствует, результат `score=null`, `UNRATED` при тех же числах.

## 13. Антифрод и независимость

**Не учитываем:** отзывы владельца о себе, ботов, дубликаты, скрытые/доказанно мошеннические отзывы. **Не удаляем негативные** за то, что владельцу не понравилась оценка; владелец может дать публичный ответ и обжаловать фактическую ошибку.

Рекомендуемые технические меры:
- soft limits на частоту отзывов;
- review-by-visit proof (QR/check-in/booking — если есть надёжный источник);
- проверка одинаковых текстов/кластера новых аккаунтов;
- IP/device anti-abuse внутри защищённого хранилища, без публичной экспозиции;
- evidence freshness и приоритет текущих условий;
- audit пересчёта и versioned datasets;
- экспертные оценки по чек-листу с конфликтом интересов.

## 14. Протокол перерасчёта и обратимости

Каждый `score_snapshot` сохраняет:


Старые снапшоты неизменяемы. Новый набор весов = **новая формула**, не изменение истории. В UI показать «методика SpotScore v1».

## 16. Тест-план (DoD)

- [ ] При отсутствии любых наблюдений `UNRATED`, `score=null`.
- [ ] Один отзыв с 5 звездами не даёт 100.
- [ ] 100 положительных анонимных отзывов не обходят антифрод по одному субъекту.
- [ ] Отзыв владельца имеет вес 0.
- [ ] Домен без данных не превращается в ноль.
- [ ] При непроверенной безопасности SpotScore не опубликован.
- [ ] Подтвержденный критический инцидент переводит в `RESTRICTED`.
- [ ] Сезонная цена не повышает автоматически `value`.
- [ ] Для cable используется **другой профиль** весов и `course_setup`.
- [ ] Два объекта одного клуба на разных спотах не получают общий score по умолчанию.
- [ ] Пересчёт детерминированный с идентичными входами и версией.
- [ ] Округление 74.5 → 75 (`half-up`), без банковского эффекта.
- [ ] Confidence/Freshness/Match/Rideability не входят напрямую в качество.
- [ ] Реклама не влияет на Score и органический RankScore.

## 17. Пилотная калибровка

На 30–50 реально проверенных клубах и электротяговых установках:

1. независимая экспертная оценка по каждому домену;
2. выборка подтверждённых отзывов;
3. сравнение результатов до/после prior;
4. inter-rater reliability экспертов;
5. sensitivity weights и порогов;
6. bias-check по стоимости, размеру клуба, популярности и географии;
7. публикуемый changelog методики.
